# Go MLOps: 10 проектов от простого к сложному

Учебный путь из 10 проектов. Каждый следующий опирается на предыдущий. В итоге получится платформа, которая оркестрирует ИИ-агентов. Go отвечает за инфраструктуру: сервинг, пайплайны, оркестрацию, наблюдаемость. Python остаётся там, где он сильнее: обучение моделей и экспорт в ONNX.

## Что нужно знать заранее

- Базовый Go: структуры, интерфейсы, горутины, каналы, `context`, обработку ошибок
- Docker и docker-compose
- Основы ML на уровне «что такое train/inference, метрики, переобучение»
- Немного Python, чтобы обучить модель и экспортировать её

## Проект 1. Inference-сервис для ONNX-модели

**Цель:** написать HTTP-сервис на Go, который загружает обученную модель и отдаёт предсказания.

**Что сделать:**
1. Обучить простую модель на Python (scikit-learn, например Iris или California Housing) и экспортировать её в ONNX через `skl2onnx`.
2. Написать Go-сервис с эндпоинтами:
   - `POST /predict` принимает JSON с фичами и возвращает предсказание
   - `GET /healthz` для liveness, `GET /readyz` для readiness (модель загружена)
3. Валидировать входные данные: размерность, типы, диапазоны.
4. Сделать graceful shutdown через `signal.NotifyContext`.
5. Собрать multi-stage Dockerfile, финальный образ на `distroless`.

**Стек:** `net/http` (Go 1.22+ routing) или `chi`, [`onnxruntime_go`](https://github.com/yalue/onnxruntime_go), `log/slog`

**Критерии готовности:**
- [ ] Покрытие unit-тестами ≥ 70%, table-driven tests
- [ ] Бенчмарк `go test -bench` для `/predict`
- [ ] Образ меньше 100 МБ (без учёта библиотеки ONNX Runtime)
- [ ] Конфигурация через переменные окружения

**Чему научишься:** структура Go-проекта (`cmd/`, `internal/`), CGO-зависимости, контейнеризация ML-сервиса.

## Проект 2. Реестр моделей (Model Registry)

**Цель:** хранить версии моделей с метаданными, чтобы inference-сервис из проекта 1 сам подтягивал нужную версию.

**Что сделать:**
1. Хранить артефакты (`.onnx`) в MinIO (S3-совместимом), метаданные в PostgreSQL: имя, версию, метрики, хэш, автора, стадию (`staging`, `production`, `archived`).
2. REST или gRPC API:
   - загрузка модели (multipart или presigned URL)
   - список версий, переход между стадиями
   - `GET /models/{name}/production` возвращает актуальную версию
3. Проверка целостности по SHA256.
4. CLI на `cobra`: `mreg push`, `mreg promote`, `mreg list`.
5. Доработать проект 1: при старте и периодически опрашивать реестр, горячо подменять модель без даунтайма (`atomic.Pointer`).

**Стек:** `pgx`, `sqlc` или `goose` для миграций, `minio-go`, `cobra`, docker-compose

**Критерии готовности:**
- [ ] Интеграционные тесты на `testcontainers-go`
- [ ] Горячая замена модели без 5xx под нагрузкой (проверить через `vegeta` или `k6`)
- [ ] Миграции БД версионируются

**Чему научишься:** работа с БД и объектным хранилищем, gRPC/protobuf, конкурентная подмена состояния.

## Проект 3. Наблюдаемость ML-сервиса

**Цель:** видеть, что происходит с моделью в проде: и технические метрики, и ML-метрики.

**Что сделать:**
1. Prometheus-метрики:
   - latency (histogram), RPS, ошибки по кодам
   - распределение предсказаний (histogram по классам или значениям)
   - версия модели как label
2. Трассировка OpenTelemetry: span на парсинг, препроцессинг, инференс, постпроцессинг.
3. Структурированные логи `slog` с `trace_id`.
4. Логировать запросы и ответы в Kafka или NATS (с сэмплированием) для последующего анализа дрифта.
5. Grafana-дашборд и алерты (p99 latency, доля ошибок, резкий сдвиг распределения предсказаний).

**Стек:** `prometheus/client_golang`, `go.opentelemetry.io/otel`, Jaeger или Tempo, Grafana, NATS JetStream

**Критерии готовности:**
- [ ] Дашборд в Grafana хранится как код (JSON в репозитории)
- [ ] Хотя бы 3 алерта в Alertmanager
- [ ] Логирование не увеличивает p99 больше чем на 5%: асинхронная отправка через буферизованный канал

**Чему научишься:** три столпа observability, middleware в Go, асинхронная обработка без потери производительности.

## Проект 4. Feature Store

**Цель:** единый источник фичей для обучения (офлайн) и инференса (онлайн), чтобы устранить train/serving skew.

**Что сделать:**
1. Описывать фичи декларативно (YAML): имя, тип, источник, TTL, сущность (`user_id`, `item_id`).
2. Офлайн-хранилище: Parquet-файлы в S3 или PostgreSQL. Point-in-time join для обучающих выборок.
3. Онлайн-хранилище: Redis с низкой задержкой чтения.
4. Материализация: воркер, который периодически переносит свежие фичи из офлайна в онлайн.
5. gRPC API `GetOnlineFeatures(entity_ids, feature_names)` с батчингом.
6. Интеграция с проектом 1: сервис получает только `user_id`, а фичи подтягивает сам.

**Стек:** `go-redis`, `parquet-go`, gRPC, `errgroup` для параллельных запросов

**Критерии готовности:**
- [ ] p99 чтения онлайн-фичей < 10 мс на 100 фичей
- [ ] Тест на отсутствие утечки данных из будущего в point-in-time join
- [ ] Метрики свежести фичей (feature freshness)

**Чему научишься:** дизайн data-интенсивных систем, train/serving skew, батчинг и пайплайнинг в Redis.

## Проект 5. Батч-пайплайн обучения (мини-Airflow)

**Цель:** собственный оркестратор DAG-пайплайнов для регулярного переобучения моделей.

**Что сделать:**
1. Описывать пайплайн в YAML: шаги `extract → validate → train → evaluate → register`, зависимости между ними.
2. Планировщик: топологическая сортировка, cron-расписание, параллельный запуск независимых шагов.
3. Шаги выполняются как Docker-контейнеры (обучение на Python, остальное на Go).
4. Очередь задач (NATS JetStream или Redis Streams), пул воркеров, ретраи с экспоненциальным backoff, таймауты.
5. Состояние запусков хранится в PostgreSQL, чтобы после рестарта можно было продолжить с упавшего шага.
6. Шаг `evaluate` сравнивает новую модель с production и регистрирует её в реестре (проект 2), только если она лучше.
7. Простой веб-UI или TUI (`bubbletea`) со статусами запусков.

**Стек:** `robfig/cron`, Docker SDK for Go, NATS, PostgreSQL

**Критерии готовности:**
- [ ] Обнаружение циклов в DAG
- [ ] Идемпотентность шагов: повторный запуск не ломает результат
- [ ] Kill воркера посреди задачи → задача перезапускается на другом воркере

**Чему научишься:** распределённые очереди, at-least-once delivery, идемпотентность, отказоустойчивость. Это фундамент для проекта 10.

## Проект 6. Детектор дрифта и A/B-роутинг

**Цель:** автоматически замечать деградацию модели и безопасно выкатывать новые версии.

**Что сделать:**
1. Сервис дрифта читает лог запросов из проекта 3 и считает по окнам:
   - data drift: PSI, KS-тест, KL-дивергенция по фичам
   - prediction drift: сдвиг распределения выходов
   - concept drift: если поступают ground truth-метки, считать деградацию метрик
2. Реализовать статистику на чистом Go (или через `gonum`).
3. Traffic router (reverse proxy на `httputil.ReverseProxy`):
   - **canary**: 5% → 25% → 100% с автоматическим откатом по метрикам
   - **shadow**: дублировать трафик на новую модель, но не отдавать её ответ
   - **A/B**: sticky-распределение по `user_id` (consistent hashing)
4. При обнаружении дрифта автоматически запускать пайплайн переобучения из проекта 5.

**Стек:** `gonum`, `httputil`, Prometheus, проекты 2, 3, 5

**Критерии готовности:**
- [ ] Синтетический тест: искусственно сдвинуть распределение и убедиться, что сработал алерт и запустилось переобучение
- [ ] Автооткат canary при росте ошибок
- [ ] Статистическая значимость в A/B (минимальный размер выборки, p-value)

**Чему научишься:** прикладная статистика, стратегии деплоя, замкнутый цикл MLOps (continuous training).

## Проект 7. Kubernetes-оператор для ML-моделей

**Цель:** декларативно деплоить модели в Kubernetes через собственный CRD.

**Что сделать:**
1. Описать CRD `ModelDeployment`:
   ```yaml
   apiVersion: mlops.example.com/v1
   kind: ModelDeployment
   metadata:
     name: fraud-detector
   spec:
     model: fraud-detector
     version: "3"          # или stage: production
     replicas: { min: 2, max: 20 }
     resources: { gpu: 0, memory: 1Gi }
     rollout: { strategy: canary, steps: [5, 25, 100] }
   ```
2. Контроллер (reconcile loop) создаёт Deployment, Service и HPA, скачивает модель через init-container из реестра.
3. Автоскейлинг по кастомной метрике (очередь запросов или RPS) через KEDA или HPA + Prometheus Adapter.
4. Перенести canary-логику из проекта 6 в оператор.
5. Статус в `.status`: текущая версия, фаза rollout, conditions.
6. Деплоить через Helm-чарт и GitOps (ArgoCD).

**Стек:** `kubebuilder`, `controller-runtime`, `kind` или `k3d`, KEDA, Helm, ArgoCD

**Критерии готовности:**
- [ ] Тесты контроллера на `envtest`
- [ ] Reconcile идемпотентен: удалил Deployment руками, оператор его восстановил
- [ ] Finalizers для корректной очистки ресурсов

**Чему научишься:** Kubernetes изнутри, паттерн контроллера, GitOps. Именно так устроены KServe и Seldon.

## Проект 8. LLM Gateway

**Цель:** единая точка доступа к нескольким LLM-провайдерам с контролем стоимости, надёжностью и наблюдаемостью.

**Что сделать:**
1. Единый API (OpenAI-совместимый формат) поверх нескольких бэкендов: Anthropic, OpenAI, локальные модели через Ollama или vLLM.
2. Стриминг ответов через SSE, корректная отмена при разрыве соединения клиентом (`context`).
3. Rate limiting по API-ключам: token bucket в Redis, лимиты и по запросам, и по токенам.
4. Fallback и retry: при 429 или 5xx переключаться на другого провайдера, circuit breaker.
5. Кэширование: точное (хэш промпта) и семантическое (по эмбеддингу, порог косинусной близости).
6. Учёт затрат: подсчёт токенов, стоимость по каждому ключу и команде, бюджеты с алертами.
7. Guardrails: маскирование PII на входе, фильтр промпт-инъекций, ограничение длины.
8. Логирование промптов и ответов для оценки качества (с маскированием).

**Стек:** официальные Go SDK провайдеров (`anthropic-sdk-go`, `openai-go`), Redis, `sony/gobreaker`, OpenTelemetry (GenAI semantic conventions)

**Критерии готовности:**
- [ ] Стриминг работает через gateway без буферизации
- [ ] Отключение основного провайдера незаметно для клиента
- [ ] Дашборд: токены, стоимость, latency до первого токена (TTFT), hit rate кэша

**Чему научишься:** LLMOps, работа со стримингом в Go, паттерны отказоустойчивости, экономика LLM.

## Проект 9. RAG-платформа с оценкой качества

**Цель:** production-grade Retrieval-Augmented Generation с измеримым качеством.

**Что сделать:**
1. **Ingestion-пайплайн** (на базе проекта 5): загрузка PDF, Markdown и HTML, чанкинг (по размеру, семантический, с перекрытием), генерация эмбеддингов, запись в векторную БД. Инкрементальная переиндексация по хэшам документов.
2. **Retrieval**: гибридный поиск (вектор + BM25), reranking, фильтрация по метаданным, мультитенантность.
3. **Generation**: сборка промпта с цитатами, вызов LLM через gateway из проекта 8.
4. **Evaluation-сервис**:
   - golden dataset из вопросов и эталонных ответов
   - метрики retrieval: recall@k, MRR
   - метрики генерации через LLM-as-judge: faithfulness, relevance, наличие цитат
   - запуск оценки в CI на каждое изменение промпта, чанкинга или модели
5. Версионирование промптов и конфигураций RAG как артефактов в реестре (проект 2).
6. Сбор обратной связи пользователей (👍/👎) и её использование для расширения golden dataset.

**Стек:** Qdrant или pgvector, gRPC, проекты 2, 5 и 8, GitHub Actions

**Критерии готовности:**
- [ ] Регрессия качества роняет CI
- [ ] Индексация 10 000 документов с параллельными воркерами и ограничением rate limit провайдера эмбеддингов
- [ ] Каждый ответ трассируется: какие чанки извлечены, какой промпт, сколько стоил

**Чему научишься:** архитектура RAG, оценка недетерминированных систем, eval-driven development.

## Проект 10. Оркестратор ИИ-агентов

**Цель:** платформа, которая запускает многошаговых ИИ-агентов надёжно, наблюдаемо и с контролем. Финальный проект объединяет всё предыдущее.

**Архитектура:**

```
                 ┌──────────────────────────┐
  API / UI ────▶ │  Orchestrator (Temporal) │
                 └────────────┬─────────────┘
          ┌───────────────────┼────────────────────┐
          ▼                   ▼                    ▼
   ┌─────────────┐    ┌──────────────┐    ┌────────────────┐
   │ Planner     │    │ Worker Agents│    │ Human-in-loop  │
   │ agent       │───▶│ (research,   │    │ approvals      │
   └─────────────┘    │  code, data) │    └────────────────┘
                      └──────┬───────┘
          ┌──────────────────┼───────────────────┐
          ▼                  ▼                   ▼
   ┌────────────┐    ┌──────────────┐    ┌──────────────┐
   │ LLM Gateway│    │ Tool Registry│    │ RAG / Memory │
   │ (проект 8) │    │ (MCP servers)│    │ (проект 9)   │
   └────────────┘    └──────────────┘    └──────────────┘
```

**Что сделать:**
1. **Durable execution**: агентный цикл (LLM → tool call → результат → LLM) как Temporal workflow. Каждый вызов LLM и инструмента является activity с ретраями. Падение воркера не теряет прогресс агента.
2. **Tool Registry**: инструменты подключаются как MCP-серверы (Model Context Protocol), написанные на Go через официальный `modelcontextprotocol/go-sdk`. Нужны JSON Schema для аргументов, валидация, таймауты, sandbox (выполнение кода в изолированном контейнере или gVisor).
3. **Мультиагентность**:
   - planner разбивает задачу на подзадачи (DAG, как в проекте 5)
   - специализированные агенты выполняют подзадачи параллельно (child workflows)
   - supervisor проверяет результаты и при необходимости отправляет на доработку
4. **Память**: краткосрочная (контекст диалога со сжатием и суммаризацией при переполнении) и долгосрочная (RAG из проекта 9).
5. **Human-in-the-loop**: опасные действия (запись в прод, отправка писем, траты) ставят workflow на паузу до подтверждения через Temporal signals.
6. **Лимиты и безопасность**: бюджет на токены, деньги и количество шагов для каждой задачи, детект зацикливания, allowlist инструментов для каждого агента, аудит-лог всех действий.
7. **Наблюдаемость**: полная трасса агента (каждая мысль, вызов инструмента, стоимость) в OpenTelemetry, UI для просмотра «дерева» выполнения.
8. **Оценка агентов**: набор задач-бенчмарков с проверяемым результатом, success rate, средняя стоимость и число шагов, регрессионный прогон в CI (подход из проекта 9).
9. **Деплой**: воркеры агентов в Kubernetes с автоскейлингом по длине очереди Temporal task queue (проект 7).

**Пример задачи для демо:** «Проанализируй дрифт модели fraud-detector за неделю, найди причину в данных, предложи и запусти переобучение». Агент использует инструменты из всех предыдущих проектов: реестр, метрики, детектор дрифта, пайплайн обучения.

**Стек:** Temporal Go SDK, MCP Go SDK, проекты 2–9, Kubernetes

**Критерии готовности:**
- [ ] `kill -9` воркера посреди задачи → агент продолжает с того же шага
- [ ] Агент не может вызвать опасный инструмент без approval
- [ ] Превышение бюджета корректно останавливает задачу с частичным результатом
- [ ] Success rate на бенчмарке отслеживается между версиями промптов и моделей

**Чему научишься:** архитектура агентных систем, durable execution, безопасность ИИ, оценка агентов. Всё вместе составляет современный AI-инжиниринг.

## Сквозные практики (применять во всех проектах)

- **CI/CD:** GitHub Actions с `golangci-lint`, `go test -race`, сборкой образа и сканированием уязвимостей (`govulncheck`, `trivy`)

- **Документация:** README с архитектурной схемой, ADR (Architecture Decision Records) для ключевых решений
- **Монорепо:** все проекты в одном репозитории с общими пакетами в `pkg/` (логгер, конфиг, телеметрия)
