# Проект 2. Реестр моделей

> **Статус:** готов и работает (`docker compose up`, реестр на `localhost:8090`, inference на `localhost:8081`)
> **Язык:** Go 1.26, PostgreSQL 17, S3-хранилище RustFS
> **Опирается на:** [проект 1](01-inference-service.md) (inference-сервис)

---

## 1. О чём проект

В первом проекте модель была вшита прямо в Docker-образ. Чтобы обновить модель, приходилось пересобирать и перезапускать сервис. Непонятно было и то, какая версия сейчас работает и как вернуть вчерашнюю.

Реестр моделей решает это так же, как библиотека решает учёт книг. У каждой модели есть карточка: номер версии, кто и когда её сдал, какие у неё метрики, контрольная сумма файла. Сами файлы лежат на складе (S3), а карточки в каталоге (PostgreSQL). Одна из версий помечена как **production**, то есть «та, что сейчас выдаётся читателям».

Inference-сервис теперь не хранит модель у себя. Раз в несколько секунд он спрашивает реестр, какая версия сейчас production. Если она сменилась, сервис скачивает новую, проверяет и подменяет **прямо на ходу**, не останавливаясь и не теряя ни одного запроса.

Итог в одной фразе: выкатить новую модель или откатить старую теперь можно одной командой `mreg promote`, без пересборки и перезапуска чего-либо.

---

## 2. Зачем это нужно

| Проблема без реестра | Как решено |
|---|---|
| Новая модель требует пересборки образа | Модель скачивается из реестра во время работы |
| Неизвестно, какая версия в работе и откуда она | У каждой версии номер, автор, дата, метрики, SHA256 |
| Откат занимает время и нервы | `mreg promote iris 1` возвращает старую версию за секунды |
| Файл мог побиться при копировании | SHA256 проверяется при загрузке в реестр и при скачивании из него |
| Две production-версии одновременно | База данных физически не даст это сделать (уникальный индекс) |
| Перезапуск сервиса рвёт запросы | Модель меняется внутри работающего процесса |

## 3. Новые термины

| Термин | Простыми словами |
|---|---|
| **Реестр моделей (model registry)** | Каталог всех версий моделей с их паспортами и стадиями |
| **Стадия (stage)** | Статус версии: `none` (просто загружена), `staging` (на проверке), `production` (в работе), `archived` (снята) |
| **Promote** | Перевод версии в другую стадию, обычно в production |
| **S3 / объектное хранилище** | «Склад файлов» с доступом по сети. Стандарт де-факто, придуман Amazon |
| **Бакет (bucket)** | Папка верхнего уровня в S3. У нас один бакет `models` |
| **SHA256** | «Отпечаток» файла. Изменился хоть один байт, и отпечаток станет другим |
| **Миграция БД** | Файл с SQL, который создаёт или меняет таблицы. Применяется автоматически при старте |
| **Горячая замена (hot swap)** | Замена модели внутри работающего сервиса без остановки |
| **Polling** | Периодический опрос: «ничего не поменялось?» |
| **testcontainers** | Библиотека, которая поднимает настоящие PostgreSQL и S3 в Docker прямо из теста |

## 4. Как устроено

```
   Разработчик / CI
        │  mreg push, mreg promote
        ▼
 ┌──────────────────┐   метаданные   ┌──────────────┐
 │  Registry (Go)   │ ─────────────► │ PostgreSQL   │  таблицы models, model_versions
 │  :8090           │                └──────────────┘
 │                  │   файлы        ┌──────────────┐
 │                  │ ─────────────► │ RustFS (S3)  │  models/iris/1/model.onnx
 └────────▲─────────┘                └──────────────┘                  .../metadata.json
          │
          │ каждые 5 с: «какая версия production?»
          │ если сменилась: скачать файлы, сверить SHA256
          │
 ┌────────┴─────────┐
 │ Inference (Go)   │  reloader → загрузка ONNX → атомарная подмена модели
 │ :8081            │  старая модель закрывается, когда доработают её запросы
 └──────────────────┘
          ▲
       клиенты
```

**Жизненный цикл версии:**
1. `mreg push iris --dir models/iris`: реестр принимает файлы, проверяет хэш, присваивает номер (v1, v2, ...), стадия `none`.
2. `mreg promote iris 2 --stage production`: v2 становится production, прежняя production уходит в `archived`. Всё в одной транзакции.
3. Inference в течение 5 секунд замечает смену, скачивает v2 и подменяет модель.
4. Откат: `mreg promote iris 1 --stage production`. Inference возвращается к v1, причём файл берётся из локального кэша без повторного скачивания.

## 5. Ход разработки: что, зачем и в каком порядке

### Этап 0. Выбор S3-хранилища

**Что произошло.** По плану хранилищем должен был быть MinIO. Но официальных образов MinIO на Docker Hub больше нет совсем, ни свежих, ни старых: компания прекратила публиковать бесплатную версию. На quay.io их тоже нет.

**Решение.** Проверили доступные S3-совместимые замены (RustFS, SeaweedFS, Garage) и выбрали **RustFS 1.0.2**. Он повторяет интерфейс MinIO: те же порты 9000 и 9001, ключи доступа через переменные окружения, веб-консоль. Версия зафиксирована тегом, а не `latest`, чтобы сборка завтра не сломалась от чужого обновления.

**Почему это не страшно.** Код работает с хранилищем через стандартный протокол S3 и Go-клиент `minio-go`. Его можно направить на AWS S3, Yandex Object Storage или вернуть MinIO, поменяв только адрес в настройках.

### Этап 1. Общие типы API

**Файл:** [`internal/registryapi/types.go`](../internal/registryapi/types.go)

Описаны структуры, которыми обмениваются сервер и клиенты: версия модели, стадии, сводка по модели. Вынесены в отдельный маленький пакет, чтобы CLI и inference-сервис не тянули к себе драйверы PostgreSQL и S3, которые им не нужны.

Здесь же правило для имени модели: строчные латинские буквы, цифры, `-` и `_`. Имя попадает в пути S3 и URL, поэтому лишние символы лучше отсечь сразу.

### Этап 2. Схема базы данных и миграции

**Файл:** [`internal/registry/migrations/00001_init.sql`](../internal/registry/migrations/00001_init.sql)

Две таблицы:
- `models`: имя модели и дата создания;
- `model_versions`: номер версии, стадия, SHA256, размер, паспорт модели (JSONB), автор, даты.

Защита от ошибок прямо в базе, а не только в коде:
- `CHECK` на допустимые стадии, формат SHA256 и имени;
- `UNIQUE (model_id, version)`: двух v3 у одной модели быть не может;
- **частичный уникальный индекс** `WHERE stage = 'production'`: у модели не может оказаться две production-версии, даже если в коде будет ошибка.

Миграции применяет библиотека **goose** при старте реестра. SQL-файлы встроены в бинарник через `go:embed`, поэтому их не нужно отдельно копировать на сервер.

### Этап 3. Слой хранения: PostgreSQL и S3

**Файлы:** [`store.go`](../internal/registry/store.go), [`blob.go`](../internal/registry/blob.go)

**Store** работает с PostgreSQL через `pgx`. Самое интересное место здесь выделение номера версии. Если два человека одновременно загружают модель, оба могут посчитать «последняя была v5, значит я v6». Чтобы этого не случилось, транзакция сначала блокирует строку модели (`INSERT ... ON CONFLICT DO UPDATE` держит блокировку до конца транзакции). Второй загружающий ждёт, пока первый закончит, и получает v7.

Перевод в production сделан так же: в одной транзакции старая production уходит в `archived`, новая становится production. Промежуточного состояния, когда production нет вообще или их две, снаружи не видно.

**Blob** работает с S3: загрузить, скопировать, прочитать, удалить файл. Копирование выполняется на стороне хранилища, данные не гоняются через наш сервис.

### Этап 4. Бизнес-логика загрузки

**Файл:** [`service.go`](../internal/registry/service.go)

Порядок шагов выбран так, чтобы в реестре никогда не появилась «битая» версия:

1. Разобрать `metadata.json` теми же правилами, что использует inference (функция `model.ParseMetadata` из проекта 1).
2. Залить `model.onnx` во **временный** ключ `uploads/<случайный id>`, по пути считая SHA256.
3. Сверить хэш с тем, что записал скрипт обучения. Не совпало, значит файл повреждён: ошибка 422, версия не создаётся.
4. В транзакции выделить номер версии, скопировать файл на постоянное место `iris/<версия>/model.onnx`, сохранить `metadata.json` уже с присвоенным номером и только потом записать строку в БД.
5. Временный файл удаляется в любом случае, даже если клиент отключился посреди загрузки.

Если падает любой шаг, транзакция откатывается и версия не появляется.

### Этап 5. HTTP API реестра

**Файл:** [`api.go`](../internal/registry/api.go)

| Метод и путь | Что делает | Нужен токен |
|---|---|---|
| `GET /v1/models` | Список моделей: последняя версия, текущая production | нет |
| `GET /v1/models/{name}/versions` | Все версии модели | нет |
| `POST /v1/models/{name}/versions` | Загрузить новую версию (multipart: `model`, `metadata`) | **да** |
| `GET /v1/models/{name}/versions/{ref}` | Версия по номеру (`3`) или стадии (`production`) | нет |
| `PUT /v1/models/{name}/versions/{n}/stage` | Сменить стадию, тело `{"stage":"production"}` | **да** |
| `GET /v1/models/{name}/versions/{n}/files/{file}` | Скачать `model.onnx` или `metadata.json` | нет |
| `GET /healthz`, `GET /readyz` | Жив ли сервис, доступна ли БД | нет |

**Авторизация.** Изменяющие запросы требуют заголовок `Authorization: Bearer <токен>`. Токен сравнивается за постоянное время (`subtle.ConstantTimeCompare`), чтобы его нельзя было подобрать, замеряя скорость ответа. Чтение открыто: inference-сервису токен не нужен.

**Ошибки** переводятся в понятные HTTP-коды: нет такой модели → 404, неправильные данные → 400, не совпал хэш → 422, нет токена → 401.

**Общий middleware.** ID запросов, логирование и защита от паники из проекта 1 вынесены в пакет [`internal/httpx`](../internal/httpx/middleware.go). Теперь их используют оба сервиса, код не дублируется.

### Этап 6. Точка входа реестра

**Файл:** [`cmd/registry/main.go`](../cmd/registry/main.go)

При старте реестр: читает настройки → подключается к PostgreSQL → применяет миграции → создаёт бакет в S3, если его нет → начинает принимать запросы.

В `docker compose` все сервисы стартуют почти одновременно, и база может быть ещё не готова. Поэтому при неудаче реестр повторяет попытку с растущей паузой (0.5 с, 1 с, 2 с, ... до 5 с) и сдаётся только через минуту.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `REGISTRY_ADDR` | `:8090` | Порт |
| `DATABASE_URL` | обязательна | Подключение к PostgreSQL |
| `S3_ENDPOINT` | `localhost:9000` | Адрес S3 |
| `S3_ACCESS_KEY`, `S3_SECRET_KEY` | обязательны | Ключи S3 |
| `S3_BUCKET` | `models` | Бакет |
| `REGISTRY_TOKEN` | пусто | Токен для записи. Пусто = запись без защиты, в лог пишется предупреждение |
| `MAX_UPLOAD_BYTES` | 256 МБ | Максимальный размер загрузки |

### Этап 7. Клиент и CLI `mreg`

**Файлы:** [`internal/registryclient/client.go`](../internal/registryclient/client.go), [`cmd/mreg/main.go`](../cmd/mreg/main.go)

Один Go-клиент используется и в CLI, и в inference-сервисе.

Две детали, которые важны в реальной работе:
- **Push** передаёт файл модели потоком через `io.Pipe`, не загружая его целиком в память. Модель на 2 ГБ отправится так же, как на 600 байт.
- **Download** пишет файлы во временную папку, сверяет SHA256 и только потом одним переименованием кладёт папку на место. В кэше никогда не окажется недокачанная модель, даже если процесс убили посередине.

CLI на библиотеке **cobra**:

```
mreg push iris --dir models/iris          загрузить новую версию
mreg list                                 все модели
mreg list iris                            версии модели с метриками
mreg promote iris 2 --stage production    сменить стадию
mreg pull iris production --out ./m       скачать с проверкой хэша
```

Адрес и токен берутся из флагов `--url`, `--token` или переменных `MREG_URL`, `MREG_TOKEN`.

### Этап 8. Безопасная горячая замена в inference

**Файл:** [`internal/server/server.go`](../internal/server/server.go)

Это самое тонкое место проекта. В первом проекте модель уже лежала в атомарном указателе, но этого мало. Представим:

1. Запрос взял ссылку на модель v1 и начал инференс.
2. В этот момент пришла v2, указатель переключился, и v1 закрыли, освободив память ONNX Runtime.
3. Запрос продолжает считать на v1, но её память уже освобождена. Процесс падает.

**Решение.** У каждой загруженной модели есть счётчик «сколько запросов сейчас ею пользуются» (на основе `sync.RWMutex`):
- запрос перед инференсом берёт «билет» (`RLock`) и возвращает его после;
- при замене указатель сначала переключается на новую модель, затем код ждёт, пока все билеты старой будут возвращены (`Lock`), и только после этого закрывает её;
- если запрос успел взять ссылку на старую модель ровно в момент её закрытия, он это видит и берёт новую.

Ещё одна деталь: тело запроса читается **до** того, как взят билет. Иначе медленный клиент, который отправляет JSON по байту в секунду, держал бы старую модель и задерживал замену.

### Этап 9. Reloader: слежение за реестром

**Файл:** [`internal/reloader/reloader.go`](../internal/reloader/reloader.go)

Каждые `REGISTRY_POLL_INTERVAL` (у нас 5 секунд) reloader:
1. спрашивает реестр, какая версия production;
2. сравнивает её **SHA256** с текущей. Сравнение по хэшу, а не по номеру, нужно, чтобы откат на старую версию тоже срабатывал;
3. проверяет, нет ли этой версии в локальном кэше с правильным хэшем. Если нет или файл повреждён, скачивает заново;
4. загружает ONNX-модель. **Если загрузка не удалась, продолжает работать на старой модели** и пишет предупреждение;
5. подменяет модель и чистит кэш, оставляя текущую и предыдущую версии для быстрого отката.

Если реестр недоступен, сервис продолжает отвечать на запросы текущей моделью. Временная авария реестра не роняет продакшен.

Inference теперь работает в двух режимах:
- `REGISTRY_URL` не задан: как в проекте 1, модель из папки;
- `REGISTRY_URL` задан: модель из реестра. Сервис стартует сразу, но `/readyz` отвечает 503, пока не загрузится первая модель. Балансировщик не пошлёт трафик на неготовый экземпляр.

При остановке сервис сначала дожидается завершения reloader и только потом выгружает модель и ONNX Runtime. Иначе reloader мог бы поставить новую модель уже после выгрузки.

### Этап 10. Тесты

| Тест | Что проверяет | Где |
|---|---|---|
| **Интеграционные тесты реестра** (6 шт.) | Загрузка и нумерация, promote с архивацией старой production, откат, скачивание с проверкой хэша, отказ при неверном хэше и плохом имени, 401 без токена, 8 параллельных загрузок получают номера 1..8 без пропусков и повторов | Локально, на **настоящих** PostgreSQL и RustFS через testcontainers |
| **Горячая замена под нагрузкой** | 16 потоков шлют запросы, модель за это время подменяется 49 раз. Ни одной ошибки, ни одного обращения к закрытой модели | Везде |
| **Проверка самого теста** | Временно убрали ожидание запросов перед закрытием модели: тест упал. Вернули: прошёл. Значит, тест действительно ловит эту ошибку | Вручную, один раз |
| **Reloader** (4 шт.) | Полный цикл версий, работа на старой модели при битой новой, откат из кэша без скачивания, повторное скачивание при повреждённом кэше, недоступный реестр | Везде |
| Race detector | Все тесты с `-race`, гонок нет | В Docker |

**Покрытие:** server 97%, config 97%, httpx 85%, model 83%, reloader 76%, реестр вместе с клиентом 73%.

Внутри Docker-сборки нет доступа к Docker, поэтому интеграционные тесты там пропускаются сами (`SkipIfProviderIsNotHealthy`) и запускаются локально.

### Этап 11. Docker Compose и проверка всей системы

**Файлы:** [`docker-compose.yml`](../docker-compose.yml), [`deploy/registry.Dockerfile`](../deploy/registry.Dockerfile), [`tools/loadgen/main.go`](../tools/loadgen/main.go)

Образ реестра собран на `distroless/static`: внутри только статический бинарник, нет даже shell. В проекте 1 distroless не подошёл из-за нативной библиотеки ONNX Runtime, а реестру она не нужна. В тот же образ положен `mreg`.

Для проверки написан нагрузочный генератор `loadgen`. Он шлёт запросы в несколько потоков и считает статусы, задержки и то, какая версия модели ответила.

**Финальный сценарий:**
1. Обучили вторую версию модели с сильной регуляризацией (`--c 0.05`). Она вышла хуже: accuracy 0.867 против 0.933. Это реалистичный случай неудачного релиза.
2. Загрузили обе версии, v1 сделали production. Inference сам её подтянул.
3. Запустили нагрузку на 30 секунд, на 8-й секунде выкатили v2, на 18-й откатились на v1.

**Результат:**

```
requests: 400465 in 30.001s (13348 rps), concurrency 32
latency: p50=2.14ms p95=4.28ms p99=6.01ms max=35.79ms
status 200: 400465
model version 1: 196511 responses
model version 2: 203954 responses
RESULT: OK (все ответы 200)
```

400 тысяч запросов, две замены модели, **ноль ошибок**. По логам inference откат на v1 прошёл без скачивания, модель взялась из кэша.

## 7. Как запустить

Нужен запущенный Docker Desktop. Команды для PowerShell из папки `mlops`.

```powershell
# 1. Поднять всё: PostgreSQL, RustFS, реестр, inference
docker compose up -d --build

# 2. Собрать CLI
go build -o bin/mreg.exe ./cmd/mreg
$env:MREG_TOKEN = "dev-token"

# 3. Загрузить модель и сделать её production
./bin/mreg.exe push iris --dir models/iris
./bin/mreg.exe promote iris 1 --stage production
./bin/mreg.exe list iris

# 4. Через ~5 секунд inference готов
curl.exe -s localhost:8081/readyz
```

Обучить другую версию и выкатить её:
```powershell
docker build -t mlops-train training
docker run --rm -v "${PWD}\models\iris-c005:/out" mlops-train --c 0.05
./bin/mreg.exe push iris --dir models/iris-c005
./bin/mreg.exe promote iris 2 --stage production
```

Проверить замену под нагрузкой (в соседнем окне делать `promote`):
```powershell
go run ./tools/loadgen -url http://localhost:8081 -c 32 -d 30s
```

Консоль хранилища: http://localhost:9001 (логин `mlops`, пароль `mlops-secret`).

Интеграционные тесты реестра (поднимут свои контейнеры и уберут за собой):
```powershell
go test ./internal/registry/ -v
```

## 9. Ограничения и что дальше

**Что сознательно упрощено:**
- **Один общий токен** на запись. В реальной компании нужны пользователи и роли: кто может загружать, а кто выкатывать в production.
- **Polling, а не push-уведомления.** Задержка выката до 5 секунд, и каждый экземпляр inference опрашивает реестр. Для десятков экземпляров это нормально, для тысяч лучше подписка на события.
- **Логи опросов шумят.** Каждый опрос пишет строку в лог реестра, а пока production нет, inference каждые 5 секунд пишет предупреждение.
- **Старые версии не удаляются** из S3. Со временем понадобится политика очистки архивных версий.
- **Нет метрик.** Сколько раз менялась модель, сколько длилась загрузка, какая версия сейчас в работе, видно только в логах.

**Следующий шаг: [Проект 3. Наблюдаемость](../go-mlops-roadmap.md#проект-3-наблюдаемость-ml-сервиса).** Добавим Prometheus-метрики (задержки, RPS, распределение предсказаний, текущая версия модели как метка), трассировку OpenTelemetry и дашборды Grafana. Тогда момент замены модели будет видно на графике.
