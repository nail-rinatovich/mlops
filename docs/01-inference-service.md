# Проект 1. Inference-сервис для ML-модели

> **Статус:** готов и работает (`http://localhost:8081`)
> **Язык:** Go 1.26 (сервис) + Python 3.12 (только обучение модели)
> **Место в программе:** первый из десяти проектов ([общая карта](../go-mlops-roadmap.md))

---

## 1. О чём проект в двух словах

Мы обучили небольшую модель машинного обучения и сделали из неё **веб-сервис**: ему отправляют данные, а он в ответ говорит, что на них, по мнению модели, изображено.

**Аналогия.** Модель похожа на опытного ботаника, который по размерам лепестков узнаёт вид цветка. Пока ботаник сидит у себя дома (модель лежит файлом на ноутбуке исследователя), пользы от него никому нет. Наш сервис сажает его в справочное окно: любая программа может прислать «вопрос» и за пару миллисекунд получить «ответ». При этом окно работает круглосуточно, не принимает заведомо бессмысленных вопросов и ведёт журнал обращений.

**Конкретная задача:** классический набор данных **Iris** (ирисы Фишера). На входе четыре числа: длина и ширина чашелистика и лепестка в сантиметрах. На выходе один из трёх видов ириса (*setosa*, *versicolor*, *virginica*) и уверенность модели в каждом варианте.

Сама задача нарочно простая: цель проекта не в том, чтобы построить умную модель, а в том, чтобы правильно **довести любую модель до работающего сервиса**. Всё построенное здесь подходит для модели кредитного скоринга, антифрода или рекомендаций, отличаться будут только входные числа.

---

## 2. Зачем это нужно

В индустрии есть известная проблема: модель отлично работает в Jupyter-ноутбуке исследователя, но до реальных пользователей так и не доходит. Между «модель обучена» и «модель приносит пользу» лежит много инженерной работы, и эту область называют **MLOps**.

Проект закрывает самый первый и самый частый её шаг, **сервинг** (serving), то есть отдачу предсказаний по сети. Попутно он отвечает на вопросы, которые задают в любой компании:

| Вопрос | Как решено в проекте |
|---|---|
| Как запустить Python-модель из сервиса на другом языке? | Модель экспортируется в универсальный формат **ONNX** |
| Как убедиться, что после переноса модель отвечает так же? | Автоматический **тест паритета** сравнивает ответы Go и Python |
| Что будет, если прислать мусор? | **Валидация**: сервис отклоняет некорректные данные с понятной ошибкой |
| Как понять, что сервис жив и готов работать? | Эндпоинты **health/readiness** для систем мониторинга и Kubernetes |
| Как разбирать инциденты? | **Структурированные логи** с уникальным ID каждого запроса |
| Что будет с запросами при перезапуске? | **Graceful shutdown**: уже начатые запросы дорабатываются до конца |
| Как запустить это где угодно одинаково? | **Docker-образ** со всеми зависимостями внутри |

## 3. Словарь терминов

| Термин | Простыми словами |
|---|---|
| **Модель** | Файл с «выученными» правилами, который по входным числам выдаёт ответ |
| **Обучение (training)** | Процесс, в котором модель подбирает свои правила по примерам с известными ответами |
| **Инференс (inference)** | Использование уже обученной модели: подали данные, получили ответ |
| **Фича (feature, признак)** | Одно входное число, например «длина лепестка» |
| **Класс** | Один из возможных ответов, например «setosa» |
| **ONNX** | Открытый формат файла модели. Обучили в Python, запускаем где угодно |
| **ONNX Runtime (ORT)** | Библиотека от Microsoft, которая умеет исполнять ONNX-модели |
| **API / эндпоинт** | «Адрес» в сервисе, на который отправляют запрос, например `/v1/predict` |
| **JSON** | Текстовый формат данных, которым обмениваются сервисы |
| **Docker-образ** | «Коробка», в которой упакованы программа и всё, что ей нужно для работы |
| **CGO** | Механизм, позволяющий Go-программе вызывать библиотеки, написанные на C/C++ |
| **Паритет (parity)** | Совпадение ответов модели в среде обучения и в среде сервиса |
| **Батч (batch)** | Несколько объектов в одном запросе: так быстрее, чем по одному |

## 4. Как это устроено

```
 ┌────────────── Этап обучения (один раз) ──────────────┐
 │                                                      │
 │  Python + scikit-learn                               │
 │  train.py ──► model.onnx      (сама модель)          │
 │           ──► metadata.json   (паспорт модели)       │
 │           ──► samples.json    (эталонные ответы)     │
 └───────────────────────┬──────────────────────────────┘
                         │ файлы кладутся в образ
                         ▼
 ┌────────────── Этап работы (постоянно) ───────────────┐
 │                                                      │
 │   Клиент ──HTTP/JSON──► Go-сервис                    │
 │   (браузер,             │                            │
 │    другой сервис)       ├─ middleware: ID запроса,   │
 │                         │  логирование, защита       │
 │                         │  от паники                 │
 │                         ├─ валидация входа           │
 │                         ├─ ONNX Runtime ──► ответ    │
 │                         └─ JSON-ответ клиенту        │
 └──────────────────────────────────────────────────────┘
```

**Путь одного запроса:**
1. Клиент отправляет `POST /v1/predict` с телом `{"instances": [[5.1, 3.5, 1.4, 0.2]]}`.
2. Сервис присваивает запросу уникальный ID и засекает время.
3. Проверяет, что тело не слишком большое и JSON корректный.
4. Проверяет данные: у каждого объекта ровно 4 числа, все конечные и в допустимом диапазоне.
5. Передаёт числа в ONNX Runtime, тот прогоняет их через модель.
6. Возвращает JSON: класс, вероятности и версию модели, которая отвечала.
7. Пишет в лог строку: метод, путь, статус, длительность, ID запроса.

## 5. Ход разработки: что, зачем и в каком порядке

Этапы идут в том порядке, в котором их стоит делать. Каждый опирается на предыдущие.

### Этап 0. Подготовка окружения

**Что сделали.** Проверили установленные инструменты и выявили ограничения:
- Go 1.26 есть.
- **Нет компилятора C (gcc).** Он нужен библиотеке `onnxruntime_go`, потому что ONNX Runtime написан на C++.
- **Python 3.6 слишком старый** для современных ML-библиотек.
- Docker установлен, но не запущен. Позже выяснилось, что **диск C: заполнен на 100%**, из-за чего Docker перешёл в режим «только чтение». Место освободили, Docker перезапустили.

**Решение.** Не ставить ничего в систему, а выполнять всё «тяжёлое» (обучение, сборку с CGO) **внутри Docker-контейнеров**. Локально на Windows работают только быстрые тесты, которым CGO не нужен.

**Зачем.** Так сборка воспроизводима: у любого человека с Docker всё соберётся одинаково, независимо от того, что установлено на его машине.

### Этап 1. Обучение модели и экспорт в ONNX

**Файлы:** [`training/train.py`](../training/train.py), [`training/Dockerfile`](../training/Dockerfile), [`training/requirements.txt`](../training/requirements.txt)

**Что делается:**
1. Загружается набор Iris (150 цветков), 20% откладывается для проверки качества.
2. Обучается связка «нормализация данных (StandardScaler) → логистическая регрессия».
3. Считаются метрики на отложенных данных: **accuracy 0.933, F1 0.933**.
4. Модель конвертируется в ONNX. Важная настройка `zipmap=False`: без неё вероятности приходят в неудобном формате «список словарей», а с ней это обычная числовая таблица.
5. Входы и выходы модели переименовываются в стабильные имена `input`, `label` и `probabilities`, потому что Go-сервис опирается именно на них.
6. Рядом с моделью сохраняются два файла:
   - **`metadata.json`** (паспорт модели): имя, версия, контрольная сумма SHA256, список фичей с допустимыми диапазонами, названия классов, метрики;
   - **`samples.json`**: 10 примеров с ответами, которые дал Python. Это эталон для проверки паритета.

**Зачем паспорт.** Сервис ничего не знает о модели заранее: имена фичей, их количество и названия классов он берёт из `metadata.json`. Значит, если завтра подложить другую модель с другими фичами, код менять не придётся.

**Зачем эталонные ответы.** При переносе модели между средами возможны тихие ошибки: перепутан порядок фичей, другой тип чисел, другая версия операторов. Модель при этом «работает», но отвечает неправильно. Эталон позволяет поймать такие ошибки автоматически.

**Результат:** папка `models/iris/` с тремя файлами.

### Этап 2. Каркас Go-проекта и конфигурация

**Файлы:** [`go.mod`](../go.mod), [`internal/config/config.go`](../internal/config/config.go)

**Что делается:**
- Создаётся модуль `mlops` со стандартной для Go структурой: `cmd/` для запускаемых программ, `internal/` для внутренних пакетов.
- Все настройки читаются из **переменных окружения** (принцип 12-factor app):

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `INFERENCE_ADDR` | `:8080` | На каком порту слушать |
| `MODEL_DIR` | `models/iris` | Где лежит модель |
| `ORT_LIB_PATH` | — | Путь к библиотеке ONNX Runtime |
| `MAX_BATCH` | `256` | Максимум объектов в одном запросе |
| `MAX_BODY_BYTES` | `1048576` | Максимальный размер запроса (1 МБ) |
| `SHUTDOWN_TIMEOUT` | `15s` | Сколько ждать завершения запросов при остановке |
| `LOG_LEVEL` | `info` | Подробность логов |

**Зачем.** Один и тот же Docker-образ можно запускать в разных средах (разработка, тест, прод) с разными настройками, не пересобирая его. Ошибочные значения, например `MAX_BATCH=abc`, обнаруживаются сразу при старте, а не в момент первого запроса.

### Этап 3. Слой модели: интерфейс и ONNX-реализация

**Файлы:** [`internal/model/model.go`](../internal/model/model.go), [`internal/model/onnx.go`](../internal/model/onnx.go), [`internal/model/onnx_stub.go`](../internal/model/onnx_stub.go)

**Что делается:**
1. Объявляется **интерфейс `Predictor`**: «нечто, что умеет делать предсказание по батчу и знает свои метаданные». HTTP-слой работает только с этим интерфейсом и не знает, что внутри ONNX.
2. Пишется реализация `ONNXPredictor`:
   - при загрузке **сверяет модель с паспортом**: у модели один вход `input` нужной ширины и выходы `label` и `probabilities`. Если модель не соответствует паспорту, сервис не стартует;
   - на каждый запрос упаковывает числа в тензор (многомерный массив), запускает модель и разбирает ответ;
   - аккуратно освобождает память C-библиотеки после каждого вызова;
   - может обрабатывать запросы из многих потоков одновременно без блокировок.
3. Пишется **заглушка** для сборки без CGO. Она позволяет компилировать и тестировать остальной код на машине без gcc.

**Зачем интерфейс.** Во-первых, HTTP-слой можно тестировать с «фальшивой» моделью, без ONNX Runtime. Во-вторых, во втором проекте модель будет подменяться на лету новой версией из реестра, и интерфейс делает это простым.

### Этап 4. HTTP API и валидация входных данных

**Файл:** [`internal/server/server.go`](../internal/server/server.go)

**Эндпоинты:**

| Метод и путь | Что возвращает | Кому нужно |
|---|---|---|
| `POST /v1/predict` | Предсказания для батча объектов | Клиентам сервиса |
| `GET /v1/model` | Паспорт загруженной модели | Людям и другим сервисам |
| `GET /healthz` | «Процесс жив» (всегда 200) | Kubernetes: перезапускать ли контейнер |
| `GET /readyz` | «Готов принимать запросы» (200, только если модель загружена) | Балансировщику: слать ли сюда трафик |
| `GET /` | Веб-страница для ручной проверки | Людям |

**Пример обмена:**
```
→ POST /v1/predict
  {"instances": [[5.1, 3.5, 1.4, 0.2]]}

← 200 OK
  {"model": {"name": "iris", "version": "1"},
   "predictions": [{"label": 0, "class": "setosa",
                    "probabilities": [0.981, 0.019, 0.0000003]}]}
```

**Проверки входа**, каждая с понятным текстом ошибки:

| Ситуация | Ответ |
|---|---|
| Тело больше 1 МБ | `413 request body too large` |
| Сломанный JSON или неизвестные поля | `400 invalid JSON: …` |
| Пустой список объектов | `400 instances must be non-empty` |
| Объектов больше лимита | `400 batch size N exceeds limit 256` |
| Не 4 числа в объекте | `400 expected 4 features, got 2` |
| Значение вне диапазона из паспорта | `400 feature "petal_width"=-2 out of range [0, 5]` |
| Модель ещё не загружена | `503 model is not loaded` |
| Внутренняя ошибка модели | `500 prediction failed`, подробности только в логе |

**Зачем такая строгость.** Модель всегда что-нибудь ответит, даже на явную бессмыслицу вроде отрицательной длины лепестка. Без проверок такой ответ выглядел бы правдоподобно и молча испортил бы решения, которые на нём основаны. Лимиты на размер защищают сервис от перегрузки одним огромным запросом.

**Важная деталь для будущего.** Текущая модель хранится в атомарном указателе (`atomic.Pointer`). Это позволяет заменить её новой версией прямо во время работы, без остановки сервиса и без единого потерянного запроса. Сейчас эта возможность не используется, но она понадобится во втором проекте.

### Этап 5. Middleware: ID запросов, логи, защита от сбоев

**Файл:** [`internal/server/middleware.go`](../internal/server/middleware.go)

Middleware — это «обёртки», через которые проходит каждый запрос до и после основной логики:

1. **Request ID.** Каждому запросу присваивается уникальный идентификатор, или берётся из заголовка `X-Request-ID`, если его прислал клиент. ID возвращается в ответе и пишется в лог. Если пользователь жалуется на ошибку, по ID можно найти именно его запрос среди миллионов.
2. **Логирование.** Для каждого запроса пишется одна строка в формате JSON с методом, путём, статусом, длительностью и ID. Запросы `/healthz` и `/readyz` пишутся на уровне debug, потому что Kubernetes дёргает их каждые несколько секунд и иначе засорил бы логи.
3. **Recoverer.** Если где-то в коде случится паника (аварийная ошибка), сервис не упадёт целиком: клиент получит `500`, а в лог попадёт описание проблемы.

**Зачем JSON-логи.** Их можно автоматически собирать и фильтровать в системах вроде Grafana Loki или ELK, например запросом «все ответы со статусом 500 за последний час».

### Этап 6. Точка входа и корректная остановка

**Файл:** [`cmd/inference/main.go`](../cmd/inference/main.go)

**Порядок запуска:** читаем конфиг → настраиваем логгер → инициализируем ONNX Runtime → загружаем модель и сверяем с паспортом → запускаем HTTP-сервер с таймаутами.

**Graceful shutdown.** Когда сервису приходит сигнал остановки (Ctrl+C, `docker stop`, перезапуск пода в Kubernetes), он:
1. перестаёт принимать новые запросы;
2. ждёт, пока доработают уже начатые (до 15 секунд);
3. освобождает модель и ONNX Runtime;
4. завершается с кодом 0.

**Зачем.** При каждом обновлении сервиса старые экземпляры останавливаются. Без graceful shutdown клиенты, чьи запросы попали на этот момент, получили бы обрыв соединения.

**Таймауты сервера** (чтение заголовков 5 с, запроса 10 с, ответа 30 с) защищают от «медленных» клиентов, которые держат соединение открытым и исчерпывают ресурсы.

### Этап 7. Тестирование

**Файлы:** [`config_test.go`](../internal/config/config_test.go), [`model_test.go`](../internal/model/model_test.go), [`onnx_test.go`](../internal/model/onnx_test.go), [`server_test.go`](../internal/server/server_test.go)

| Вид теста | Что проверяет | Где запускается |
|---|---|---|
| Unit-тесты конфига | Значения по умолчанию, переопределения, ошибки в значениях | Везде |
| Unit-тесты API | Все 13 сценариев запроса (успех, каждая ошибка валидации, паника, 503), пробы, ID запросов, подмена модели | Везде (с фальшивой моделью) |
| **Тест паритета** | Go + ONNX Runtime дают те же классы и вероятности (точность 0.0001), что и Python, на 10 эталонных примерах | В Docker (нужен CGO) |
| Конкурентный тест | 32 потока × 50 запросов одновременно, все ответы корректны | В Docker |
| Race detector (`-race`) | Нет гонок данных между потоками | В Docker |
| Бенчмарки | Скорость обработчика и инференса | Написаны, но ещё не запускались |

Тесты написаны в стиле **table-driven**: каждый сценарий — строка в таблице, так новые случаи легко добавлять.

**Покрытие кода тестами:** server 98%, config 96%, model 83% (цель была ≥ 70%).

### Этап 8. Docker-образ

**Файлы:** [`deploy/inference.Dockerfile`](../deploy/inference.Dockerfile), [`.dockerignore`](../.dockerignore)

**Многоэтапная сборка (multi-stage):**
1. **Этап `ort`:** скачивается официальная сборка ONNX Runtime 1.29.0 с GitHub. Версия должна точно совпадать с той, под которую написана Go-библиотека `onnxruntime_go` v1.36.0.
2. **Этап `build`:** в образе с Go и gcc **прогоняются все тесты** (с `-race` и тестом паритета) и компилируется бинарник. Если хоть один тест упал, образ не соберётся.
3. **Финальный этап:** в чистый минимальный Debian копируются только бинарник, библиотека ORT и модель. Компиляторов и исходников в нём нет. Сервис запускается **не от root**, а от непривилегированного пользователя.

**Зачем многоэтапность.** Инструменты сборки весят больше гигабайта, но в работе не нужны. Финальный образ меньше, быстрее скачивается и содержит меньше потенциальных уязвимостей.

**Проблема, с которой столкнулись.** Изначально финальный образ строился на `distroless` от Google: это ультраминимальная база без оболочки и пакетного менеджера, образ получался 86 МБ. Но ONNX Runtime **падал при старте с ошибкой сегментации**, хотя все нужные ему системные библиотеки были на месте. Тот же бинарник в обычном `debian:bookworm-slim` работал стабильно. Причину найти не удалось, поэтому база заменена на Debian slim (образ 163 МБ), а находка задокументирована в Dockerfile.

### Этап 9. Ручная проверка в работе

Контейнер запущен и проверен вживую:

| Проверка | Результат |
|---|---|
| `/healthz`, `/readyz` | 200, видна версия модели |
| Батч из трёх цветков разных видов | Все три вида определены верно |
| Отрицательная длина лепестка | 400 с указанием поля и допустимого диапазона |
| Неполные данные / сломанный JSON / GET вместо POST | 400 / 400 / 405 |
| `docker stop` | В логах `shutting down` → `stopped`, код выхода 0 |
| Время предсказания | ~2.5 мс внутри сервиса |

### Этап 10. Веб-страница для людей

**Файл:** [`internal/server/ui/index.html`](../internal/server/ui/index.html)

Изначально по адресу `http://localhost:8081/` открывалось `404 page not found`, потому что сервис был чистым API. Для удобства добавлена страница: поля для четырёх фичей (диапазоны подтягиваются из паспорта модели), кнопки-пресеты с типичными цветками каждого вида, полоски с вероятностями, время ответа и ID запроса. HTML встроен прямо в бинарник (`go:embed`), так что отдельные файлы раздавать не нужно.

**Зачем.** Чтобы проверить модель, не нужно знать curl или JSON: можно открыть браузер и подвигать числа. Это полезно для демонстраций и для быстрой проверки после деплоя.

## 7. Как запустить с нуля

Нужен только запущенный Docker Desktop. Команды для PowerShell, из папки `mlops`:

```powershell
# 1. Обучить модель (результат появится в models/iris)
docker build -t mlops-train training
docker run --rm -v "${PWD}\models\iris:/out" mlops-train --version 1

# 2. Собрать образ сервиса (внутри прогонятся все тесты)
docker build -f deploy/inference.Dockerfile -t mlops-inference:dev .

# 3. Запустить (порт 8080 у нас занят другим проектом, поэтому 8081)
docker run -d --name inf -p 8081:8080 mlops-inference:dev

# 4. Проверить
curl.exe -s -X POST localhost:8081/v1/predict -d '{\"instances\":[[5.1,3.5,1.4,0.2]]}'
```

Или просто открыть в браузере **http://localhost:8081**.

Быстрые тесты без Docker (без ONNX-части):
```powershell
go test -cover ./...
```

## 9. Ограничения и что дальше

**Чего в проекте сознательно нет:**
- **Модель зашита в образ.** Чтобы обновить модель, нужно пересобрать образ. Неудобно, если модели обновляются часто.
- **Нет версионирования моделей.** Непонятно, какая версия была в работе неделю назад и как к ней откатиться.
- **Нет метрик.** Логи есть, но графиков задержек, нагрузки и распределения ответов нет.
- **Нет авторизации.** Сервис доступен любому, кто достучится до порта.

**Следующий шаг: [Проект 2. Реестр моделей](../go-mlops-roadmap.md#проект-2-реестр-моделей-model-registry).** Модели будут храниться в отдельном хранилище (MinIO) с версиями и паспортами в базе данных (PostgreSQL). Inference-сервис научится сам подтягивать актуальную версию и **подменять модель на лету без остановки**, используя уже заложенный атомарный указатель. Метрики и графики появятся в третьем проекте.
